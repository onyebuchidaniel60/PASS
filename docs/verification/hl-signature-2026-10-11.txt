Exit code: `1`.

## What this proves

- The order action shape was accepted far enough for Hyperliquid to
  attempt signer recovery: the response names the recovered agent address
  (`0x2e98…bfb`), which matches the key that signed. A malformed EIP-712
  payload or a wrong signing domain fails before recovery with
  `Unable to recover signer` — that is not what happened.
- The L1 phantom-agent signing path (Exchange domain, chain 1337,
  `signL1Action`) works end to end against mainnet from this codebase.
- The request reached Hyperliquid's account lookup over the live
  Exchange API. The lookup found no such user or agent.
- The only missing piece is the deposit that creates the account on
  Hyperliquid: an unfunded, never-approved throwaway wallet has no
  on-chain record, so there is no balance to check yet. With the same
  agent approved from a funded master account, the next rejection past
  this point is the balance check — which is the acceptance proof for a
  funded fill.

## What this does not prove

- The fill, the position, or the TP/SL legs. Those require a funded
  account and remain unproven (see `docs/EXECUTION_READINESS.md`).
- Anything about the PASS server relay beyond the shared signing code:
  the relay was deliberately bypassed here. The relay proof awaits a
  funded account (Stage F acceptance test).
